# Car Hero — تطبيق الفنّي (Provider)

واجهات مزوّد الخدمة الميداني، مبنيّة على **نفس بنية `car-hero-app`** (تطبيق
العميل): Expo + React Native، عربية RTL، خط Cairo، ونفس رموز التصميم.

## التشغيل

```bash
npm install
npm run web      # أو: npm run android / npm run ios
```

## طبقة التصميم — كيف يبقى التطبيقان متطابقين

الطبقة المشتركة (`AppText` · `ui.js` · `feedback.js` · `validators.js` ·
`useReducedMotion` · `qa.js` · **وشاشات استعادة كلمة المرور الأربع**)
**منسوخة حرفياً** من `car-hero-app`، و`theme.js` منسوخ حرفياً في أوّل ١٧٨
سطراً ثم تأتي إضافات الفنّي تحتها. الانحراف يُكشف بأمر واحد:

```bash
cd ..
for f in src/components/ui.js src/components/AppText.js \
         src/services/feedback.js src/services/qa.js \
         src/services/validators.js src/hooks/useReducedMotion.js \
         src/screens/Auth/ForgotPasswordScreen.js \
         src/screens/Auth/OtpScreen.js \
         src/screens/Auth/ResetPasswordScreen.js \
         src/screens/Auth/PasswordChangedScreen.js; do
  diff -q "car-hero-app/$f" "car-hero-app-provider/$f"
done
# رأس theme.js يجب أن يطابق ملف العميل كاملاً:
head -n 178 car-hero-app-provider/src/theme/theme.js \
  | diff - car-hero-app/src/theme/theme.js
```

**فحص الأيقونات قبل كل إضافة:** أيقونة غير موجودة في `phosphor-react-native`
تصل `undefined` ولا يشتكي المُجمِّع منها إطلاقاً — تظهر صفحة بيضاء عند فتح
الشاشة فقط. (هكذا كانت `TowTruck` تُعطّل «بدء التوجيه» و«سابقة» كلياً.)
للتأكّد من اسم أيقونة:

```bash
grep "icons/Truck'" node_modules/phosphor-react-native/src/index.tsx
```

**لهذا لا يُضاف شيء إلى `ui.js`.** ما يخصّ الفنّي وحده يعيش في
`providerUi.js` مبنيّاً **فوق** أوّليات `ui.js` لا بجانبها — وإلا انكسرت
المقارنة أعلاه وصار نقل التحسينات بين التطبيقين تخميناً.

### إضافات `theme.js` للفنّي

| الرمز | الدور |
|---|---|
| `gradients.success` | الأخضر = **تقدّم** لا نجاح: قبول الطلب، بدء الخدمة، إنهاؤها |
| `gradients.night` | خلفية الطلب الوارد وحده — المقاطعة الوحيدة في التطبيق |
| `gradients.calm` | خلفية الإتمام: تهدئة لا احتفال |
| `onDark.*` | نصوص وطبقات زجاجية فوق الداكن — `textMuted` يختفي هناك |
| `providerColors.*` | أسطح لا مقابل لها عند العميل (حلقة «غير متصل»، الخريطة، مسار المبدّل) |
| `providerRadius.*` | استدارة بطاقات الفنّي — أوسع عن قصد: بطاقة واحدة كبيرة لا قوائم كثيفة |
| `providerMotion.*` | نافذة الردّ (٢٠ث) وإيقاع نبضة «متصل» |

## `providerUi.js` — التركيبات

`ProviderScreen` · `ScreenTitle` · `Card` · `IconTile` · `ServiceRow` ·
`DetailRow` · `StatTile` · `Segmented` · `GradientButton` · `GlassButton` ·
`HaloIcon` · `GradientOrb` · `MapCanvas` · `BottomSheet` · `FloatingBar`

`ProviderScreen` هو جذر كل شاشة ويشتقّ حشوتها من `useSafeAreaInsets`.
و`navClearance(insets.bottom)` هي المساحة التي تحجزها الشاشات ذات الشريط
السفلي أسفل محتواها.

**طبقتان في `ProviderScreen`:** الخلفية (لون أو تدرّج) تملأ الشاشة، والمحتوى
يجلس في عمود محصور بـ`layout.contentMaxWidth` ومتوسّط — نفس ثلاثية
`ui.screenContent` في تطبيق العميل. بدونها كانت شاشات الفنّي تتمدّد إلى حافة
الشاشة على الويب واللوحي بينما يبقى العميل في عمود 560. شاشة الخريطة وحدها
تمرّر `wide` فتُلغي الحصر، لأن تطبيق العميل لا يحصر خرائطه أيضاً
(`InteractiveMapScreen` · `ProvidersMapScreen`). و`ProviderNav` يتوسّط فوق
العمود نفسه لا يتمدّد وحده.

## استعادة كلمة المرور — أربع شاشات منسوخة حرفياً

```
Login → ForgotPassword (رقم) → Otp (رمز ٦ خانات) → ResetPassword → PasswordChanged → Login
```

الشاشات الأربع **نسخ حرفية** من تطبيق العميل، ولهذا تُقاد بعقد الخصائص نفسه
(`onSubmit` · `onBack` · `onLogin` · `loading` · `error`) لا بكائن `nav`:
تحويلها إلى أسلوب `navigation` كان يكسر مقارنة الـdiff ويجعل نقل أي تحسين
لاحق (وهي أعلى شاشات التسرّب في أي تطبيق) تخميناً.

**الحالة في الجذر لا في الشاشات:** الرقم يعبر ثلاث شاشات، وحفظه داخل إحداها
يعني تمريره يدوياً أو إعادة سؤال المستخدم عنه في أسوأ لحظة — بعد فشل دخوله.

| قرار | لماذا |
|---|---|
| الدخول باسم مستخدم والاستعادة برقم الهاتف | الرقم هو ما يملك الفنّي وسيلة استقباله (واتساب)، واسم المستخدم تختاره الإدارة وقد لا يذكره أصلاً |
| «تعديل الرقم» يعود إلى `ForgotPassword` لا إلى الدخول | الخطأ في الرقم أشيع أسباب عدم وصول الرمز، والعودة للدخول تجعله طريقاً مسدوداً |
| «تواصل مع الدعم» في ورقة الرمز ← اتصال بالإدارة | حساب الفنّي من الإدارة، فهي جهة الدعم الفعلية لا صندوق بريد عام |
| `PasswordChanged` يصفّر المكدّس | الرجوع إلى رمز مستهلَك أو كلمة مرور حُفظت شاشتان ميّتتان |

**لا خادم بعد:** كل معالج في `App.js` ينتقل محلّياً وموضع النداء معلّم بـTODO.
عند الربط تُنسخ `authApi.js` من تطبيق العميل وتُستبدل أجسام المعالجات وحدها —
الشاشات لا تُلمس لأنها تتلقّى `loading`/`error` كخصائص أصلاً.

## `PastRequestScreen` — سجلّ الطلب المنتهي

شاشة مستقلّة عن `RequestDetailsScreen` عن قصد: الأخيرة شاشة **عمل** — شارتها
«مقبول» وأسفلها «بدء التوجيه» — وفتحُها لطلب أُغلق قبل أسبوع يعرض إجراءً لا
محلّ له. فهذه للقراءة فقط **وبلا زرّ إجراء إطلاقاً**، لأن أي زرّ يُضاف سيكون
إمّا بلا وظيفة أو موحياً بأن الطلب ما زال قابلاً للتعديل.

- `steps` بأوقاتها هي قلب الشاشة لا زينتها: هي ما يُسأل عنه الفنّي بعد أيام.
  الخطوة الفاشلة تحمل ✕ وأحمر — لا ✓ أخضر مثل سابقاتها.
- **الملغى بلا تفصيل مالي**: «٠ ل.س» تُقرأ خدمة مجّانية لا خدمة لم تقع،
  فيحلّ محلّها سبب الإلغاء.
- بيانات الطلب مصدرها `PAST_REQUESTS` وحده، وقائمة «طلباتي» تشتقّ بطاقاتها
  منه — نسختان للطلب نفسه كانتا ستجعلان تعديل إحداهما يقول التطبيق شيئين.

## التنقّل — لا مكتبة تنقّل

`ProviderNavigator.js` الأصلي (react-navigation) **استُبدل** بالراوتر اليدوي في
`App.js`، وهو نمط تطبيق العميل نفسه: حالة `step` واحدة، ومكدّس `navStack` يحفظ
الخطوة ومعاملاتها معاً، وكائن `nav` يحاكي واجهة react-navigation
(`navigate` / `replace` / `goBack` / `reset` / `popToTop`) فتبقى الشاشات مكتوبة
بأسلوبها المألوف دون أن يعتمد التطبيق على المكتبة.

خريطة الأسماء ← الخطوات في `ROUTE_TO_STEP` أعلى `App.js`. **إضافة شاشة تحتاج
ثلاثة تعديلات هناك:** الاستيراد، ومدخل في الخريطة، وشرط الرسم.

**شاشات الشريط السفلي** (`home`, `myRequests`, `notifications`, `profile`)
تُبدَّل كجذر لا تُدفع للمكدّس، وإلا نما المكدّس بلا حدّ مع كل تنقّل بين تبويبين.

### مسار دورة الطلب

```
Login → Home (تشغيل الاتصال) → NewRequest (نافذة ردّ ٢٠ ثانية)
      → RequestDetails → EnRoute → Arrived → InService → Completed → Home
```

زرّ «محاكاة وصول طلب» في `HomeScreen` (حالة «متصل») هو مدخل التجربة، ولا يظهر
إلا في `__DEV__`، ويُحذف عند ربط البثّ اللحظي.

## ما تغيّر عن الملفات الأصلية

| التغيير | السبب |
|---|---|
| `Text` من `react-native` ← `components/AppText` | خط Cairo يُشتقّ من وزن النصّ بدل تركه لخط النظام |
| التدرّجات المكتوبة يدوياً ← رموز `gradients` | `theme.js` هو مكان القرار البصري |
| البنفسجي `#8f5cb1/#6a1b9a` ← `gradients.primary` | توحيد الهوية مع تطبيق العميل |
| شعار «CH» النصّي ← `assets/carhero-logo.png` | الشعار الرسمي واحد ولا يُرسم له بديل |
| `ProviderNavigator.js` ← راوتر `App.js` | بنية واحدة عبر التطبيقين |
| **`paddingTop: 52` في ١١ شاشة ← `ProviderScreen`** | الرقم الثابت يصيب هاتفاً ويخطئ ما عداه: يقصّ المحتوى تحت النتوء ويهدر الفراغ على القصيرة |
| **`Pressable` خام ← `PressableScale`** | لا انكماش عند اللمس ولا اهتزاز — والاثنان مجّانيان في الطبقة المشتركة |
| **٢٥ لوناً حرفياً ← `onDark` و`providerColors`** | لون في ملف شاشة يعني قراراً بصرياً خارج `theme.js` |
| **`fontWeight: '800'` (٥٢ موضعاً) ← `font.weight.bold`** | Cairo محمّل بأربعة أوزان تنتهي عند 700؛ ما فوقه يُحلّ إليه فيوهم بوزن غير موجود |
| **أحجام ونصف أقطار حرفية ← `font.size` و`spacing` و`providerRadius`** | ١٤.٥ و١٣.٥ و١٢.٥ لم تكن سُلّماً بل تقريباً متكرّراً |
| **`Modal` خامّة ← `ConfirmSheet`** | خلفية غير قابلة للإغلاق، بلا دور `alert`، وزرّ إلغاء أضيق من هدف اللمس |
| **شارة الحالة الثابتة ← `StatusPill`** | كانت خضراء دائماً مهما كانت الحالة، فيبدو الطلب الملغى ناجحاً |
| **`TextInput` خامّة ← `InputField`** | بلا حالة خطأ ولا ربط `aria-describedby` ولا تسلسل تركيز |
| **صفر خصائص وصول ← أدوار وأسماء وحالات** | أزرار الاتصال والمراسلة كانت دوائر صامتة تماماً لقارئ الشاشة |
| **`StatusBarScrim` مركّب في الجذر** | `edgeToEdgeEnabled: true` يجعل النصّ يصعد خلف الساعة والبطارية عند التمرير |
| **الشريط السفلي `bottom: 14` ← `insets.bottom + 14`** | كان يقع تحت شريط إيماءات النظام فتصير تبويباته غير قابلة للّمس |
| **«د.أ» ← `services/money.js`** | الفنّي والعميل كانا يريان عملتين مختلفتين للمبلغ نفسه |
| **«IN_SERVICE» ← «قيد التنفيذ»** | رمز داخلي للخادم عُرض للفنّي كما هو |
| **«00:12:34» ثابتة ← عدّاد حيّ** | مدّة معطّلة تُقرأ كخلل لا كتصميم |
| **«تحديد الكل كمقروء» ← زرّ يعمل** | كان نصّاً داخل `Pressable` بلا `onPress` إطلاقاً |
| **انتهاء نافذة الردّ ← يعود للرئيسية** | كان العدّاد يقف على صفر وزرّ القبول ما زال يوهم بأنه فعّال |
| **`TowTruck` ← `Truck` (شاشتان)** | `TowTruck` **غير موجودة في phosphor**: تصل `undefined` فتُسقط الشاشة إلى صفحة بيضاء. كانت «بدء التوجيه» وتبويب «سابقة» يعطّلان التطبيق كلياً. و`Truck` هي أيقونة السحب في تطبيق العميل |
| **`onPress={() => {}}` ← `services/contact.js`** | أربعة أزرار اتصال ومراسلة تنكمش وتهتزّ ولا تفعل شيئاً — أسوأ من زرّ معطّل، لأن الفنّي يظنّ الاتصال جارياً فينتظر |
| **«نسيت كلمة المرور؟» ← تدفّق الاستعادة الكامل** | كان نصّاً بلا `onPress` إطلاقاً. الشاشات الأربع منسوخة حرفياً من تطبيق العميل |
| **بطاقات التنبيهات ← تُفتح وتُعلَّم مقروءة** | كانت بطاقات صامتة: التنبيه يقول «تم تعيينك للطلب #1042» ولا سبيل لفتحه. الآن نفس عقد `openNotification` عند العميل — وما لا وجهة له يبقى بطاقة لا زرّاً |
| **اسم العميل الحرفي (٤ شاشات) ← `services/demo.js`** | رقم هاتفه لم يكن موجوداً أصلاً، ولهذا لم يكن لزرّ الاتصال ما يتّصل به |
| **عرض المحتوى غير محصور ← `layout.contentMaxWidth`** | التطبيقان كانا بتخطيطين على الويب واللوحي: العميل في عمود 560 والفنّي ممتدّ إلى الحافة |
| **أرقام أردنية (+962) ← سورية (+963)** | تطبيق العميل كلّه سوري: `PhoneField` يفرض الصيغة و`validatePhone` يرفض ما عداها والعملة `ل.س`. كان الفنّي والعميل يريان بلدين |
| **اسم الفنّي مكتوباً في شاشتين ← `demo.PROVIDER`** | تغييره في إحداهما يجعل التطبيق ينادي الفنّي باسمين |
| **أيقونة الخدمة تُختار في كل شاشة ← `serviceIcon.js`** | الخدمة الواحدة كانت تظهر برمزين مختلفين حسب الشاشة التي فُتحت منها |
| **بطاقات «سابقة» معطّلة ← `PastRequestScreen`** | كانت تبدو بطاقات صامتة بلا مخرج؛ والسجلّ هو ما يُحتكم إليه بعد أيام |

## غير مربوط بعد — **كل البيانات في الشاشات ثابتة**

هذه واجهات فقط. لم يُنقل أيّ من طبقة الخدمات في تطبيق العميل، عن قصد: عقود
الفنّي في الخادم لم تُراجَع بعد، ونقل `api.js` بلا التحقّق منها يعني اختراع
عقود. المطلوب لاحقاً:

1. **`services/api.js` + `config.js` + `tokenStorage.js`** — تُنسخ من تطبيق
   العميل كما هي (تجديد التوكن وفكّ `{success,data}` والمهلة مشتركة).
2. **`AuthContext` + `authApi`** — دخول الفنّي باسم مستخدم لا برقم هاتف، ولا
   تسجيل ذاتي (الحساب يُنشأ من الإدارة)، فالسياق يحتاج مراجعة لا نسخاً.
   ومعالجات الاستعادة في `App.js` (`handleForgotPassword` · `handleOtpConfirm` ·
   `handleResetPassword`) معلّمة بـTODO عند موضع النداء بالضبط.
3. **مفتاح الاتصال (`online`)** في `HomeScreen` — حالة محلّية الآن؛ يجب أن تصير
   نداء خادم، لأن `GET /providers/nearby` يُرجع المتصلين فقط، أي أن هذا المفتاح
   هو ما يجعل الفنّي مرئياً للعملاء أصلاً.
4. **الطلب الوارد** — نافذة الـ٢٠ ثانية تعمل محلّياً بلا مصدر؛ تحتاج قناة
   `socket.io` (نظير `createOrdersSocket` في تطبيق العميل) ومهلة يحسمها الخادم
   لا العميل. الرمز `providerMotion.responseWindow` هو نقطة الاستبدال.
5. **الخرائط** — `MapCanvas` ترسم طرقاً كعناصر `View`. تطبيق العميل يستعمل
   Leaflet داخل `WebView` (`InteractiveMapScreen`)، ونفس الأسلوب هو الأقرب هنا.
   جمعُها في مكوّن واحد يجعل الاستبدال تعديل ملف واحد لا أربع شاشات.
6. **الحالات الأربع** — الشاشات لا تعرض تحميلاً/خطأً لأنها لا تجلب شيئاً. عند
   الربط: `AsyncContent` من `ui.js`، ولا تُبنَ يدوياً. (حالة الفراغ مركّبة
   أصلاً عبر `EmptyState` في «طلباتي» و«التنبيهات».)
7. **العملة** — `services/money.js` يعرض `ل.س` تبعاً لتطبيق العميل؛ يُحسم
   نهائياً مع الخادم.
8. **المراسلة** — `contact.messageNumber` يفتح رسالة نصّية مؤقّتاً. تطبيق
   العميل يراسل عبر محادثة داخلية (`chatApi` + `ChatScreen`)، وعند نقلها
   يُستبدل جسم تلك الدالة وحدها ولا تُلمس الشاشات المستدعية.
9. **`PastRequestScreen`** — تقرأ من `PAST_REQUESTS` في `demo.js`. عند الربط
   تصير `GET /provider/orders/:id`، و`steps` تُشتقّ من سجلّ الحالات في الخادم
   (نظير `fetchOrderStatusHistory` عند العميل) لا من بيانات ثابتة.

## اختبار الحالات

`?qa=<step>` على الويب في وضع التطوير يقفز إلى أي شاشة مباشرة — مفاتيح الخطوات
في `ROUTE_TO_STEP` داخل `App.js`. مثال: `?qa=inService`. تُلغى تلقائياً خارج
`__DEV__`.
